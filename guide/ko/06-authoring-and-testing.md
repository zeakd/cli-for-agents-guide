# 6. 제작과 검증

## 명령 선언

입력·설명·실행·출력 형식은 한 명령의 정의를 구성한다. 이 정의에서 파싱·검증·도움말·스키마를 생성하면 같은 사실을 여러 곳에 다시 작성하지 않아도 된다. 명령 설명과 입력 계약은 필수로 두고, 출력은 기본 계약을 제공하되 대체 형식을 선언하게 한다.

레지스트리와 기능별 폴더는 이를 구현하는 방법이다. 명령 하나가 반드시 파일 하나에 들어갈 필요는 없다. 변경에 필요한 정의와 사용 지식을 함께 찾을 수 있도록 구성한다.

## 사용 지식의 조립

사용 지식을 기능 가까이에 두고 작업별로 조립할 수 있다.

```text
deploy/
├─ 공통 안내
│  └─ 배포 실패를 조사하는 흐름
├─ list
│  ├─ 입력·출력 선언
│  └─ 조사할 배포를 찾는 방법
├─ inspect
│  ├─ 입력·출력 선언
│  └─ 상태 해석
└─ logs
   ├─ 입력·출력 선언
   └─ 실패 로그 조회
```

명령 이름·인자·기본값은 선언에서 가져온다. 사용 상황·주의점·결과 해석은 제작자가 작성한다. 같은 명령이 여러 스킬에 포함되면 동일한 지식 조각을 참조할 수 있다.

명령 설명을 이어 붙이는 것만으로 작업 흐름이 만들어지지는 않는다. 순서와 분기, 조합에 필요한 설명은 별도로 작성한다. 프레임워크는 그 설명 안에 관련 선언과 명령별 지식을 펼쳐 보여줄 수 있다. 파일 구조와 조립 API는 구현에서 정한다. 도구 수준의 사용 지식을 제공하되 모든 명령에 별도 스킬을 요구하지는 않는다.

## 의존성 분리

입력으로 결정을 계산하는 로직과 파일·네트워크·시계·출력에 접근하는 코드를 나눈다. 환경 의존성은 컨텍스트나 함수 인자로 전달하면 전역 패치 없이 테스트에서 교체할 수 있다.

순수 함수는 입력과 반환값만으로 검증한다. 핸들러는 필요한 의존성을 주입해 특정 오류나 응답을 재현한다. 환경이 필요 없는 함수에 공통 형태를 맞추기 위한 컨텍스트를 추가할 필요는 없다.

예상 가능한 실패는 빠짐없이 처리하기 쉬운 형태로 표현한다. 결과값·판별 유니온·타입이 있는 예외 등 내부 표현은 언어와 구현에 따라 선택할 수 있다.

## 검증 경계

| 대상 | 주요 검증 |
| --- | --- |
| 순수 함수 | 입력에 따른 계산과 반환값 |
| 핸들러·서비스 | 주입된 의존성과의 상호작용 |
| 실제 CLI | 인자 전달, 설정 로딩, 출력 채널, 종료 코드, 저장 결과 |

실제 CLI 테스트는 함수 테스트만으로 확인할 수 없는 연결 부분을 검증한다. 상태를 가진 도구는 임시 홈을 사용할 수 있고, 다른 도구는 임시 입력이나 테스트 접속 대상을 사용할 수 있다.

저술된 사용 지식을 검토하고 동작 예시를 검증한다. 스킬 파일이 있거나 명령 이름이 들어 있다는 사실만으로 유용성을 확인할 수는 없으며, 기계 검사만으로도 충분하지 않다. 기계 검사는 누락된 참조와 잘못된 예제 결과를 찾을 수 있다. 대표 작업을 에이전트에게 수행하게 하면 필요한 스킬을 찾는지, 관련 없는 스킬을 선택하지 않는지, 올바른 호출을 구성하고 알려진 조합을 사용하는지 살펴볼 수 있다.

호출 횟수와 시간은 정확성과 함께 평가한다. 필요한 확인을 생략해서 빨라진 경우와 불필요한 왕복을 줄인 경우를 구분한다. 검증 방법은 반복 실행할 수 있게 문서화하되, 모든 도구에 같은 규모의 평가 체계나 모든 사례의 중복 테스트를 요구하지 않는다.
