# 6. 만들고 검증하기

## 기능의 정의를 모은다

명령을 추가할 때 같은 사실 때문에 파싱·라우팅·도움말·스키마·오류 문구를 각각 고치게 하지 않는다. 설명·입력·실행·출력 선언을 모으고, 기계적으로 만들 수 있는 표면은 그 정의에서 생성한다.

레지스트리는 이런 선언을 연결하는 유용한 방법이다. 기능별 폴더는 관련 코드를 가까이 두는 유용한 방법이다. 각 기능을 반드시 파일 하나에 담거나 모든 구현이 같은 디렉터리 구성을 따를 필요는 없다. 무관한 코드를 읽거나 중복된 사실을 관리하지 않고 기능을 이해하고 변경할 수 있게 하는 것이 목표다.

## 결정과 효과를 분리한다

결정을 계산하는 로직과 파일·네트워크·시계·출력에 접근하는 코드를 구분한다. 컨텍스트 객체나 함수 인자처럼 명시적인 경계로 외부 의존성을 전달한다.

순수 함수는 입력과 반환값만으로 확인할 수 있다. 환경이 필요 없는 코드에 컨텍스트를 넘기지 않는다. 효과를 수행하는 핸들러는 필요한 능력만 담은 좁은 컨텍스트를 받을 수 있다. 프레임워크는 전역 패치 없이 의존성을 교체하기 쉽게 해야 한다.

예상 가능한 실패는 나열하고 처리하기 쉬워야 한다. 결과값·판별 가능한 유니온·타입이 있는 예외 등이 가능한 방법이다. 요구사항은 빠짐없고 인식 가능한 실패 처리다. TypeScript의 관례가 모든 언어의 규칙은 아니다.

## 적절한 경계에서 테스트한다

```text
순수 함수        -> 입력과 반환값
명령·서비스      -> 주입된 가짜 의존성
실제 CLI         -> 격리된 환경, 실제 호출과 출력
```

함수 테스트는 메모리 저장소·가짜 HTTP 응답·고정 시계를 사용할 수 있다. 실제 환경을 준비하지 않고도 정확한 조건을 만들 수 있다.

CLI 테스트는 함수 테스트만으로 확인할 수 없는 경계를 검증한다. 인자 전달·설정 로딩·stdout과 stderr·종료 코드·실제 저장이 해당한다. 상태를 가진 도구는 임시 홈을 사용할 수 있다. 다른 도구는 임시 입력이나 테스트 접속 대상을 사용할 수 있다. [7장](07-conditional-patterns.md)에서 이 선택들을 다룬다.

변경에 맞는 검증을 사용한다. 모든 테스트를 한 프로세스에서 실행하거나 모든 사례를 모든 수준에서 중복하지 않는다. 유지하는 에이전트가 문서에 없는 수동 준비에 의존하지 않고 관련 검사를 반복 실행할 수 있어야 한다.

## 사실은 생성하고 저술된 지식은 검증한다

명령 설명과 입력 계약은 요구한다. 기본 출력 계약을 제공하고 대체 형식은 선언하게 한다. 명령마다 별도 스킬을 요구하지 않으면서 도구 수준의 사용 지식을 제공한다.

프레임워크는 누락된 선언을 찾고 생성된 표면을 비교할 수 있다. 그러나 스킬 파일이 존재하거나 명령 이름이 들어 있다는 이유만으로 산문이 유용하다고 판단할 수는 없다. 저술된 안내를 검토하고 동작 예시를 검증한다. 실행 가능한 문서 예제와 출력 fixture는 약속을 동작과 맞추는 데 도움이 된다.

## 사용 지식을 조립한다

사용 지식을 하나의 별도 문서에서만 관리할 필요는 없다. 명령의 선언과 관련 지식을 기능 가까이에 두고, 호출자가 읽을 때 작업에 맞게 조립할 수 있다.

```text
deploy/
├─ 공통 사용 지식
│  └─ 배포 실패를 조사하는 흐름
├─ list
│  ├─ 입력·출력 선언
│  └─ 조사할 배포를 찾는 방법
├─ inspect
│  ├─ 입력·출력 선언
│  └─ 상태를 해석하는 방법
└─ logs
   ├─ 입력·출력 선언
   └─ 실패 로그를 좁혀 읽는 방법
```

| 종류 | 예시 | 유지 방법 |
| --- | --- | --- |
| 선언된 사실 | 명령 이름·인자·기본값·출력 형식 | 선언에서 생성 |
| 저술된 지식 | 사용 상황·해석·주의점·명령 간 관계 | 제작자가 작성하고 검토 |

작업별 안내는 필요한 명령의 선언과 지식 조각을 참조할 수 있다. 같은 명령이 여러 스킬에 등장해도 동일한 설명을 따로 작성하고 유지하지 않게 한다.

명령별 설명을 단순히 이어 붙이는 것만으로 작업 흐름이 만들어지지는 않는다. 어떤 순서로 조합하는지, 어디서 결과에 따른 판단이 필요한지 같은 연결 지식도 제작자가 작성해야 한다. 제작할 때는 기능 가까이에, 읽을 때는 작업에 맞게 구성한다. 파일 구조와 조립 API는 구현이 선택한다.

## 사용 지식도 검증한다

사용 지식은 존재 여부뿐 아니라 발견·사용·정확성의 관점에서 검증한다.

| 수준 | 확인할 것 |
| --- | --- |
| 발견 | 이름과 설명으로 필요한 스킬을 선택할 수 있는가? |
| 사용 | 안내를 읽고 올바른 호출과 조합을 구성할 수 있는가? |
| 정확성 | 안내와 예제가 실제 동작과 일치하는가? |

기계 검사는 누락된 참조, 존재하지 않는 명령, 예제의 실행 결과 등을 확인할 수 있다. 이것만으로 설명의 유용성이 보장되지는 않는다.

에이전트 사용이 중요한 도구는 실패한 배포의 로그 찾기 같은 대표 작업으로 실제 사용을 평가할 수 있다. 필요한 스킬을 찾는지, 관련 없는 스킬을 선택하지 않는지, 알려진 절차를 불필요하게 여러 호출로 나누는지 관찰한다.

호출 횟수와 소요 시간은 정확성과 함께 평가한다. 빠르게 끝났더라도 필요한 확인을 생략하거나 잘못된 대상을 변경했다면 좋은 결과가 아니다. 모든 CLI에 같은 규모의 평가 체계를 요구하지 않는다.
