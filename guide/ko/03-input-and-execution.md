# 3. 입력과 실행

## 입력 검증

명령을 호출하기 전에 위치 인자·옵션·허용값·기본값·필수 입력을 확인할 수 있어야 한다.

```sh
tool report export sales --format csv
```

이 명령이 보고서 이름을 필수로 받고 `json`과 `csv`만 지원한다면 도움말과 실행이 같은 규칙을 따라야 한다. 구조화된 계약을 제공한다면 거기에도 같은 규칙을 설명한다.

모르는 명령이나 옵션, 빠진 값, 잘못된 타입, 초과 위치 인자는 오류로 처리한다. 요청 일부만 받아들이고 성공하면 호출자는 의도한 작업이 수행됐다고 오해할 수 있다.

```text
Invalid value: --format yaml
Allowed values: json, csv
```

오류에는 잘못된 부분과 수정에 필요한 정보를 담는다. 가까운 후보를 제안할 수 있지만 자동으로 대체해 실행하지 않는다. 해당 오류의 설명으로 충분할 때는 전체 도움말을 붙일 필요가 없다. 허용값 등을 구조화된 오류 상세로 제공하면 산문에서 추출하지 않아도 된다.

일반 인자는 공통 선언에서 파싱·검증·설명을 생성하는 방식이 유용하다. 특수한 표현식에 별도 파서가 필요하다면 문법을 설명하고 같은 입력·오류 계약을 지켜야 한다.

## 대상 조회 전에 검증하기

호출만으로 판단할 수 있는 오류는 세션을 찾거나 저장소를 열거나 서비스에 접속하기 전에 거절한다. `wait --until provider:sleeping`이 로컬에서 아는 상태 목록에 없는 이름이라면 대상이 존재하지 않아도 입력 오류를 먼저 보고한다. 상태 목록 자체를 대상에서 받아야 한다면 로컬 문법 검사인 것처럼 다루지 않고 실행에 의존하는 검사임을 설명한다.

대상 하나를 받는 명령은 `read a b`에서 `a`를 읽기 전에 요청을 거부한다. 호출자가 여러 단어의 대상을 따옴표로 묶으려 했다고 추측하지 않는다. 초과 입력과 허용 개수를 설명한다. 여러 대상은 명령이 그렇게 선언한 경우에만 유효하다.

개별 값과 함께 옵션의 충돌·의존 관계도 설명한다. 서로 반대인 표현 방식을 명시적으로 요청했을 때 한쪽이 조용히 덮어쓰게 하지 않는다. `--timeout`이 `--wait`를 요구한다면 그 관계를 설명하고 검사한다. 옵션을 제공했다는 사실과 최종 값을 구분한다. 0과 false도 유효한 입력일 수 있으며 기본값은 호출자가 옵션을 직접 제공했다는 증거가 아니다. 관계를 선언하는 정확한 문법은 각 구현이 정한다.

## 파일과 stdin

중첩된 설정은 많은 옵션보다 파일로 전달하는 편이 다루기 쉽다.

```sh
tool deploy create --input-file deployment.json
```

지원하는 형식과 예제를 제공하고, 파일과 옵션을 함께 받는 경우에는 우선순위를 정하거나 충돌을 거절한다.

```text
Invalid value at containers[0].healthcheck.intervalSeconds
Expected: a positive integer
Received: -1
```

stdin을 지원한다면 입력 형식과 필수 여부, 읽는 조건을 명시한다. stdin을 선택하지 않은 호출은 열린 입력 파이프의 EOF를 기다리지 않는다. 호출을 먼저 검증하고 선택된 입력을 읽고 검사한 뒤 작업에 필요한 자원을 만든다. 다음 예시에서는 `--input-file -`가 stdin을 선택한다.

```sh
tool deploy export api |
  tool deploy validate --input-file -
```

일반 호출은 확인 질문을 포함해 예상하지 못한 질문이나 메뉴를 열지 않는다. 필수 입력이 빠졌다면 필요한 값을 설명하고 실패한다. 대화형 진행은 별도의 명시적 선택으로 제공할 수 있다. 선언된 stdin이나 명시적으로 요청한 대기는 이런 질문과 구분한다. 그 동작은 선택 전에 발견할 수 있어야 한다.

## 명령 조합

에이전트가 명령을 개별적으로 호출하면 각 호출 사이에 결과를 읽고 다음 요청을 구성하는 과정이 들어간다. 출력에 따라 새로운 판단이 필요한 작업에는 이 과정이 필요하다. 정해진 순서로 데이터를 전달하기만 하는 작업에서는 불필요한 왕복이 된다.

앞의 내보내기·검증 예시에서 에이전트는 중간 JSON을 복사하지 않고 최종 검증 결과를 확인한다. 자주 사용하는 조합은 개별 명령의 도움말과 함께 작업별 스킬에 포함한다.

다음 단계가 성공 여부에만 달려 있다면 성공 후 이어서 실행할 수 있다. 서로 독립적인 조회는 병렬로 수행할 수 있다. 다만 비동기 제출의 성공은 작업 완료를 뜻하지 않는다. 다음 단계에 완료된 결과가 필요하면 상태 조회나 대기를 거쳐야 한다.

파이프 연결에는 형식의 호환성과 실패 처리도 필요하다. 이 조건은 [다음 장](04-results-and-presentation.md#파이프와-스트림)에서 다룬다.
