# 4. 결과와 표현

## 기본 출력

일반 실행 명령은 JSON을 기본으로 반환한다. 출력 형식은 TTY 여부로 전환하지 않는다. 에이전트도 터미널에서 실행할 수 있고, 사람도 출력을 파일이나 다른 프로그램에 전달할 수 있다.

사람용 표현은 `--human`으로 선택한다.

```sh
tool repo list
tool repo list --human
```

표현은 표·목록·글 등 결과에 맞게 달라질 수 있지만 실행 내용과 성공 판정은 같다. 프레임워크가 기본 표시를 제공하면 명령별 렌더러는 필요할 때만 추가하면 된다. `--human`은 대화형 입력을 켜지 않는다.

도움말과 스킬은 텍스트나 Markdown으로 제공할 수 있다. 파일 내용이나 다른 프로그램에 전달할 레코드를 내보내는 명령은 그 페이로드를 stdout에 직접 출력한다. 파일 경로 목록, CSV 내보내기, JSONL 로그는 호출자가 매번 결과 봉투를 벗겨야 하는 형태보다 선언한 형식 그대로 전달하는 편이 유용할 수 있다.

페이로드 형식과 지원하는 표현 옵션은 호출 전에 확인할 수 있어야 한다. 내보내는 데이터 자체가 목적에 맞는다면 별도의 사람용 표현은 필요하지 않다. 지원하지 않는 옵션은 무시하지 않고 거절한다.

## 출력 채널과 종료 코드

기본 JSON 계약에서는 성공과 실패 결과를 stdout으로 보낸다. 호출자는 두 경우 모두 같은 스트림에서 결과를 읽는다. 진행 상황과 부가 진단은 stderr로 분리한다.

stdout이 페이로드인 명령은 오류를 stderr로 보낸다. 파일 바이트나 레코드 사이에 오류 또는 성공 봉투를 넣으면 페이로드 계약이 달라지며, 데이터가 손상되거나 수신 측에서 구분하기 어려워질 수 있다.

| 출력 계약 | stdout | stderr |
| --- | --- | --- |
| 일반 JSON 결과 | 성공 또는 실패 결과 | 진행 상황과 부가 진단 |
| 페이로드 | 선언한 형식의 데이터 | 오류, 진행 상황, 부가 진단 |

호출 대상이 페이로드 명령으로 식별됐다면, 인자·옵션 등 로컬에서 확인할 수 있는 입력은 작업이나 페이로드 출력을 시작하기 전에 검증한다. 이 오류는 stderr로 보고하고 stdout은 비워 둔다. 데이터를 읽거나 처리하는 중에야 발견할 수 있는 오류는 아래의 부분 출력 계약을 따른다. 명령을 식별하지 못한 라우팅 실패는 CLI가 문서화한 공통 오류 계약을 따른다. 예상 가능한 실패와 예상 밖의 예외 모두 호출자가 실패로 인식할 수 있어야 한다. stderr에 오류와 진단을 함께 보낸다면 전체 스트림이 JSON 문서 하나라고 약속하기보다, 둘을 어떻게 구분하는지 설명한다.

JSON 내보내기도 페이로드일 수 있으며, JSON 문법이라는 사실만으로 결과 봉투가 있는 것은 아니다. 한 명령이 결과 봉투와 페이로드 형식을 모두 제공한다면 각 형식의 채널 계약과 잘못된 형식 선택을 보고할 채널을 밝힌다. 모든 형식이 페이로드라면 같은 stderr 오류 계약을 적용한다.

실패는 0이 아닌 종료 코드로도 알린다. 여러 작업 단위를 수행하는 명령은 실패 후 계속할지 중단할지 정하고, 성공·실패·미처리 범위를 보고한다. 시도한 단위에 실패가 있으면 기본 종료 코드는 0이 아니다. 작업 완료를 약속하는 명령은 필수 항목이 미처리이거나 결과가 불확실하게 남은 경우에도 성공으로 끝내지 않는다.

완료, 입력 오류, 애플리케이션 실패, 내부 실패, 실행 중단을 포함해 호출자가 종료 상태와 오류 상세로 무엇을 구분할 수 있는지 문서화한다. 모든 범주에 서로 다른 숫자 코드를 요구하지는 않으며, 신호에 의한 종료는 호스트 환경에도 영향을 받는다.

접수만 담당하는 명령은 요청 접수 성공에 0을 반환할 수 있다. 이때 결과에는 아직 작업이 완료되지 않았음을 표시한다. 선택한 전체 범위의 내보내기를 약속하는 페이로드 명령은 그 범위의 데이터를 생성하고 쓰는 일을 끝낸 뒤 완료를 보고해야 한다. 완료는 선언한 종료 상태로 알리고, 처리 범위 요약을 제공한다면 페이로드 레코드 사이가 아닌 stderr나 별도로 선언한 채널에 둔다.

## 출력 범위

목록에서 대상을 고르는 단계에는 식별자와 상태만으로 충분할 수 있다. 선택한 대상을 조사할 때는 상세 설정이나 로그가 필요할 수 있다. 목록과 상세 조회를 나누면 호출자가 처음부터 모든 객체의 내용을 읽지 않아도 된다. 목록에는 선택에 필요한 정보를 남기고, 상세 조회에 사용할 식별자와 경로를 제공한다.

긴 로그도 관련 실패와 요약을 먼저 제공할 수 있다. 어느 경우든 호출자는 결과가 전체인지, 일부인지, 요약인지 구분할 수 있어야 한다.

```text
Returned: 20 of 143 deployments
Next page: tool deploy list --cursor page-2
```

도메인에 맞는 개수 제한·필드 선택·상세 수준으로 호출자가 출력량을 조절할 수 있게 한다. 항목 생략과 내용 축약은 다르게 표시한다. 페이지가 남아 있다면 다음 조회 경로를, 내용을 요약했다면 원문이나 상세 조회 경로를 제공한다. 더 자세한 정보를 얻을 수 없다면 그 한계도 알린다. 출력량을 줄이더라도 결과의 의미를 바꾸는 사실은 숨기지 않는다.

## 파이프와 스트림

조회 결과에는 상태와 후속 행동이 포함될 수 있다. 다른 명령에 설정만 전달하려면 전용 `export` 경로를 제공하거나 필드를 추출할 수 있게 하고, 어느 부분이 수신 명령의 입력 계약에 해당하는지 설명한다.

파일 경로를 다른 프로그램의 인자로 전달할 때는 구분자와 지원하는 파일명을 정한다. 한 줄에 경로 하나를 쓰는 형식은 개행이 들어 있는 파일명을 모호함 없이 표현할 수 없다. 기본 `xargs`는 공백과 따옴표도 해석한다. NUL로 구분하는 모드를 `xargs -0`와 함께 쓰면 이 문자들을 보존할 수 있다. 아래 예시는 GNU xargs를 사용하며, `-r`은 경로 목록이 비었을 때 검색을 실행하지 않게 한다([옵션 설명](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html)).

```sh
tool files --null | xargs -0 -r rg -n -- 'error'
```

이 파이프라인은 인자 전달을 보여주는 예시이며 완전성을 확인하지는 않는다. 완전성이 중요하면 생산자와 수신자의 실패를 확인한다. GNU xargs는 검색 명령의 “일치 항목 없음”과 일반 오류 종료 상태를 모두 123으로 바꾸므로, 이 파이프라인의 종료 상태만으로는 둘을 구분할 수 없다([종료 상태 설명](https://www.gnu.org/software/findutils/manual/html_node/find_html/Invoking-xargs.html)). 구분이 필요하면 이를 보존하는 래퍼를 사용하거나 검색을 직접 실행한다.

많은 레코드는 JSONL로 물리적인 한 줄에 객체 하나를 담아 전달할 수 있다. 들여쓰기로 줄을 나누지 않고 각 레코드를 직렬화하면 문자열 안의 개행은 이스케이프된다. 원본 레코드를 다시 조회할 수 있는 식별자도 포함한다. 텍스트 검색은 직렬화된 표현을 검색하므로 개행, 따옴표, 역슬래시, 비ASCII 문자의 이스케이프 여부에 따라 문자 그대로의 검색 결과가 달라질 수 있다. 검색 용도가 중요하면 인코딩과 이스케이프 규칙을 밝힌다. TSV 내보내기도 필드 안의 탭과 개행을 표현하는 규칙이 필요하다.

큰 내보내기 결과를 전부 메모리에 만들지 않도록 레코드를 한 건씩 생성해 흘려보낸다. 수신 측은 계약이 허용하는 경우 도착한 레코드부터 처리하며, 전체 입력을 먼저 검증해야 한다면 디스크에 임시 저장하거나 입력 크기 제한을 정할 수 있다. 수신 측이 느리면 무제한으로 대기열을 늘리기보다 생산 속도를 늦춰야 한다. 개별 레코드도 클 수 있으므로, 크기 제한이나 큰 내용을 조회하는 다른 방법을 정하고 조용히 잘라내지 않는다.

```sh
tool records export --format jsonl |
  tool records validate --input-format jsonl --input-file -
```

스트림 생산자는 완료·실패 신호를 설명한다. 이미 쓴 바이트는 되돌릴 수 없다. 생성 도중 실패하면 이미 출력한 데이터는 전체 결과의 앞부분으로 남으며, 출력 오류나 갑작스러운 종료로 마지막 레코드가 불완전하게 전달되거나 버퍼에 남은 데이터가 유실될 수도 있다. 레코드 단위 형식이라는 사실만으로 각 레코드가 통째로 전달되는 것은 아니다. 감지한 실패는 stderr와 0이 아닌 종료 코드로 알리지만, 갑작스러운 종료는 이 보고도 막을 수 있다. 수신 측이 의도적으로 읽기를 일찍 끝내는 경우는 아래의 별도로 선언한 정책을 따른다. 일반 레코드 뒤에 오류 객체를 덧붙이지 않는다.

입력의 끝은 생산자의 성공을 보장하지 않는다. 생산자가 일부 레코드를 출력한 뒤 실패해도 수신 명령에는 입력 종료로 보일 수 있다. 생산자가 바이트를 썼다는 사실만으로 수신 측의 소비나 저장을 입증할 수도 없다.

전체 입력이 필요한 작업은 전체 출력을 보장하는 생산자의 종료 상태, 데이터와 별도 채널에 있거나 선언한 형식에 정의된 완료 표시, 예상 건수 등으로 완전성을 확인해야 한다. 문서의 문법이 완전하다는 사실만으로 요청한 전체 범위가 포함됐음을 입증할 수는 없다. 파이프라인의 실패 상태를 확인해도 수신 명령이 이미 수행한 변경은 남는다. 변경 명령은 전체 입력과 생산자의 완료를 검증한 뒤 실행할지, 항목별로 처리하고 부분 결과를 보고할지 정해야 한다.

수신 측은 처음 몇 개의 레코드만 고르는 경우처럼 의도적으로 읽기를 일찍 끝낼 수 있다. 생산자는 닫힌 파이프를 어떻게 처리하는지 밝히고, 불필요한 생성을 멈추면서 자원을 정리한다. 수신 측의 조기 종료 후에도 생산자가 성공으로 끝나는 정책이라면 그 성공이 전체 출력을 보장하지 않는다고 밝힌다. 이는 선택한 전체 범위의 내보내기를 약속하는 계약과 다르다. 이 정책에서는 생산자나 수신자의 종료 상태만으로 완전성을 입증할 수 없다. 전체 결과가 필요한 호출자는 예상 건수나 선언한 완료 표시 같은 별도 증거를 확인하거나, 성공이 전체 내보내기를 약속하는 명령을 사용해야 한다.

내보내기 명령의 도움말에는 형식, 레코드의 의미, 채널, 완료 계약을 함께 보여준다. 아래 예시는 수신 측의 조기 종료를 실패로 처리하는 전체 내보내기 계약을 선택했다.

```text
Output:
  UTF-8 JSONL; one log block object per line, without pretty-printing.
  Non-ASCII text is written directly as UTF-8.
  sessionId  Session containing the block
  blockId    Identifier used to retrieve the original block
  text       Block text; embedded newlines are JSON-escaped
  stdout contains only records. Errors go to stderr.
  A failed run may leave a partial prefix, including an incomplete last record.
  Exit 0 means this command wrote all selected records.
  A closed pipe while writing is a failure; check the receiver's status too.
```

필드는 결과 봉투가 있다고 가정하지 않고 각 레코드를 기준으로 설명한다. 지원하는 형식과 표현 옵션은 입력 설명 곁에 나열한다.
