# 4. 결과와 표현

## 유용한 기본값을 선택한다

일반 실행 명령은 기본적으로 JSON을 반환한다. stdout이 터미널인지 파이프인지에 따라 기계용·사람용 형식을 바꾸지 않는다. 에이전트도 터미널을 사용하고 사람도 출력을 리다이렉트한다.

같은 결과를 사람이 읽기 좋은 형태로 요청할 때 `--human`을 사용한다.

```sh
tool repo list
tool repo list --human
```

표현은 글·표·목록일 수 있다. 실행 내용이나 성공·실패의 의미는 바뀌지 않아야 한다. 프레임워크는 일반 명령에 기본 표시를 제공해 전용 렌더러 없이도 `--human`이 동작하게 해야 한다. 제작자는 명령별로 더 적합한 렌더러를 추가할 수 있다. 사람용 모드는 질문을 켜지 않는다.

도움말과 스킬은 읽는 표면이므로 텍스트나 Markdown을 사용할 수 있다. 출력 자체가 목적물인 명령은 원문·CSV·바이너리·스트림 같은 다른 형식을 선언할 수 있다. 형식과 지원하는 표현 옵션을 호출 전에 드러낸다. 지원하지 않는 옵션을 조용히 무시하지 않고 거절한다.

## 출력 채널을 예측 가능하게 한다

기본 JSON 계약에서는 성공·실패 결과 모두 stdout으로 제공한다. 호출자는 성공 여부와 관계없이 하나의 결과 스트림을 파싱할 수 있다. 진행 상황과 부가 진단은 stderr로 분리해 구조화된 결과를 깨뜨리지 않게 한다. 종료 코드도 실패를 알린다. 성공한 실행은 0, 실패는 0이 아닌 코드를 사용한다.

stdout이 목적물이나 payload 스트림인 경우 오류는 stderr에 보낸다. 파일 바이트에 오류 envelope나 진행 메시지를 끼워 넣지 않는다. 어떤 계약을 적용할지는 출력 선언이 정한다.

이는 의미에 대한 계약이며 envelope 필드 이름의 명세는 아니다. 예상 가능한 실패와 예상 밖의 예외 모두 실패로 인식할 수 있어야 한다. 내부의 예외·결과값 관례는 [6장](06-authoring-and-testing.md)에서 다룬다.

## 무엇이 성공했는지 말한다

요청 접수와 작업 완료는 다르다. 제출 자체가 성공했다면 종료 코드 0을 반환하면서 작업은 아직 진행 전이나 진행 중이라고 명확히 알릴 수 있다. 백그라운드 작업 전체가 끝났다고 표현해서는 안 된다.

일괄 명령처럼 여러 작업 단위를 수행하는 명령은 일부 성공을 허용할 수 있다. 실패 후 계속할지 중단할지는 명령 계약이 정한다. 성공·실패·미처리 범위를 알리고 일부 실패를 전체 성공으로 표시하지 않는다. 시도한 작업 단위 중 하나라도 실패하면 기본 종료 코드는 0이 아니다. 요청한 작업을 완료하는 계약의 명령은 필수 작업 단위가 미시도이거나 결과가 아직 불확실할 때도 0이 아닌 코드를 반환한다. 접수만 담당하는 명령은 앞서 설명한 것처럼 접수 성공을 별도로 알릴 수 있다.

## 사실을 숨기지 않으면서 출력량을 제한한다

큰 출력은 중요한 정보를 묻히게 하고 추론을 어렵게 한다. 다음 판단에 필요한 내용을 반환하고, 상세 내용을 읽는 명시적 경로를 제공한다.

| 결과 | 유용한 기본 출력 | 확장 |
| --- | --- | --- |
| 많은 객체 | 핵심 필드로 제한된 목록 | 다음 페이지와 객체 상세 |
| 긴 실행 로그 | 요약과 관련 실패 | 전체 로그 또는 선택한 범위 |
| 큰 문서 | 요청한 절 또는 요약임을 밝힌 내용 | 원문 |

항목 생략과 내용 축약을 구분한다. 부분 결과나 요약임을 밝힌다. 다음 페이지·상세 조회 등 확장 경로를 제공하고, 더 자세한 정보가 없다면 그것도 알린다. 잘린 결과를 전체처럼 표현하거나 의미를 바꾸는 사실을 숨기지 않는다.

개수 제한·기간·필드 선택·상세 수준은 도메인에 맞게 정할 수 있다. 공통 요구는 출력량을 통제할 수 있고 반환 범위를 정직하게 알리는 것이다.

## 조합할 수 있는 출력

일반 조회 결과와 다른 명령에 전달할 목적물은 다를 수 있다.

```sh
tool deploy get api
```

조회 결과에는 상태·설명·후속 행동이 포함될 수 있다. 반면 전용 내보내기 명령은 배포 설정 자체를 출력하도록 설계할 수 있다.

```sh
tool deploy export api
```

이 경로는 수신 명령이 기대하는 형식에 맞춰 데이터를 전달하기 쉽게 한다. 일반 결과에서 필요한 부분을 추출하는 방식도 가능하지만, 어떤 부분이 입력 계약에 해당하는지 명확해야 한다.

스트림을 제공한다면 형식과 완료·실패 신호를 설명한다.

```sh
tool records export --format jsonl |
  tool records validate --input-format jsonl --input-file -
```

여기서는 한 줄이 하나의 레코드다. 그러나 입력이 끝났다는 사실만으로 생산자가 전체 출력을 성공적으로 마쳤다고 단정할 수는 없다. 앞 명령이 중간에 실패했을 수도 있다.

일반 파이프 자체는 작업 전체의 성공을 보장하지 않는다. 전체 입력의 완전성이 중요한 작업은 생산자의 종료 상태를 확인하거나, 완료 표시·예상 건수 검증 등 적절한 장치를 사용한다. 셸의 파이프라인 실패 상태는 실행 후 실패를 알릴 수 있지만, 수신 명령이 이미 받은 바이트로 작업하는 것을 막지는 않는다. 변경을 수행하는 수신 명령은 전체 입력과 생산자의 완료를 검증한 뒤 실행할지, 항목별로 처리하고 부분 결과를 보고할지도 정한다.
